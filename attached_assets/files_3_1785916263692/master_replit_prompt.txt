   PRICING MODEL — per meal, not per full day. Every meal includes

     (a) meals per day: 1, 2, or 3 (button group)
     (b) plan length, which sets BOTH the rate per meal AND the

           - Single Day — ₦20,000/meal — fixed at exactly 1 day
           - Weekly — ₦15,000/meal — 4 to 7 days
           - Two-Week — ₦14,000/meal — 7 to 14 days

     (c) number of days actually wanted, within that plan's allowed

   ₦315,000. 1 meal/day × 4 days (the Weekly floor) = ₦60,000.

   DELIVERY TIMING — RESOLVED, no longer inconsistent with the rest of
   the site (this closes a gap flagged several times earlier in this
   spec). Healthy Meals deliberately does NOT use the same-day/rush
   model that Book a Meal and Trays & Platters use — there is no
   same-day option here at all, for any reason, no rush fee available
   to buy one. Every plan's first delivery needs a minimum of 24
   hours' notice, full stop — the date picker's minimum selectable
   date is always tomorrow, regardless of what time it currently is;
   today is never selectable, not even late at night when 24 hours
   would technically land the next morning anyway. This is deliberate:
   an ongoing subscription doesn't have the same "I need this
   specific thing urgently, tonight" case that a one-off soup or
   platter order does, and the 24-hour floor exists specifically to
   give the kitchen real breathing room for a standing commitment.
   Because delivery is always at least a full day out, every plan's
   Day 1 already has a complete day ahead of it before the first

11. ORDER STATUS TRACKING — two new pages, "order-status.html"
    (customer-facing) and "staff-order-links.html" (internal, for
    riders/kitchen staff only — noindex, not linked from any
    customer-facing nav). NOTE: this started as a single-purpose
    "arrival countdown" feature and was expanded to 4 stages — if
    you see an older reference anywhere to "staff-arrival-link.html"
    (singular purpose), that file was renamed/replaced, update the
    reference rather than recreate the old file.

    THE PROBLEM THIS SOLVES: the client wants customers to see
    order-progress updates — Preparing, Dispatched, Arrived,
    Delivered — without building a full backend/admin system. A
    static site has no server to run a clock, hold order state, or
    push a notification, so none of this can work by "the site
    detects what stage the order is at." It works by a different
    mechanism entirely — READ THIS BEFORE CHANGING ANYTHING HERE:

    THE MECHANISM — each stage update is its own independently
    generated link, not one page that updates itself. staff-order-
    links.html has 4 buttons, one per stage. Tapping any button
    builds a link to order-status.html with either a `stage` query
    param (preparing / dispatched / delivered — simple static
    states) or, for the Arrived stage specifically, a `start` param
    holding the exact current timestamp (Date.now(), milliseconds —
    this one needs a live countdown, not just a static message, see
    below). That link is sent to the customer over WhatsApp (a human
    action — the "Open in WhatsApp" button opens a pre-filled wa.me
    message with the link already in it, same pattern used
    everywhere else on this site). This is why it needs no backend:
    the page's entire state is fully determined by which link the
    customer happens to be viewing — there's no order database, no
    session, no memory between page loads, and none is needed.
    IMPORTANT — staff choose which stages to actually use per order.
    Not every order needs all 4 links sent: a quick, simple order
    can skip straight to Dispatched; a large or slow order (a
    Platter, a Party Starter, a first Healthy Meals drop) benefits
    from using all 4, since the added reassurance matters more when
    there's more elapsed time and more money on the line. Build all
    4 buttons as always-available tools — do not make the UI imply
    they're a mandatory sequence that must all be tapped in order
    for every single order.
    ALSO NOTE: order confirmation itself ("Booked") is deliberately
    NOT one of the 4 stages — the itemized WhatsApp confirmation a
    customer already receives immediately on placing an order already
    serves that purpose. Adding a separate "Booked" stage link would
    just duplicate a message they already get automatically — don't
    add a 5th button for it.

    ORDER-STATUS.HTML STATES (six total):
      - No "stage" or "start" param at all → "Your order is on the
        way" — generic friendly waiting message (this is also the
        fallback for a malformed/unrecognized URL).
      - stage=preparing → "Your order is being prepared."
      - stage=dispatched → "Your order is dispatched" (on its way,
        arrival update to follow).
      - start=<timestamp>, less than 15 minutes elapsed → shows a
        live MM:SS countdown, updating every second via setInterval
        (not a one-time render — it must visibly tick). Under 3
        minutes remaining, switch to an "urgent" visual style (color
        change) as an extra visual cue. This is the ONLY stage that
        needs the live-countdown treatment — the other 3 stages are
        static messages with no timer.
      - start=<timestamp>, 15+ minutes elapsed (including if the
        link is opened AFTER the window already closed, e.g. a
        customer checks it late) → "Waiting time has expired" state,
        with a WhatsApp button pre-filled to request redelivery
        (which per policy incurs a new delivery fee, no free second
        attempt).
      - stage=delivered → "Delivered — enjoy your meal!" (a distinct
        positive/success visual style, not the same neutral style as
        the waiting states).
    If a request somehow includes BOTH a "start" param and a "stage"
    param, "start" (the countdown) always takes priority, since
    arrival is the most time-sensitive state to get right.
    KNOWN BUG, ALREADY FIXED, DON'T REINTRODUCE: an early version
    referenced the setInterval ID inside the tick() function before
    it had been assigned (a const declared after the first call to
    tick()), which threw "Cannot access before initialization" on
    the exact case where a link is opened already-expired. Declare
    the interval variable with `let` BEFORE the first tick() call,
    assign it after — don't restructure this back to a single const
    declared inline with setInterval().

    STAFF-ORDER-LINKS.HTML — deliberately no nav, no customer-facing
    styling polish, `<meta name="robots" content="noindex">`, not
    linked from anywhere a customer could stumble onto it. Has ONE
    text input at the top ("Who is this message going to?") where
    staff type the correct name for THIS specific message — either
    the person who ordered, or their designated recipient, whichever
    one is actually being contacted for that delivery. This is
    plain manual entry, typed once per order, not pulled
    automatically from anywhere — there is no OCR, no payment
    receipt reading, no database lookup; a static site has no way to
    read a name off an image. What it DOES do: that name
    auto-populates into whichever stage message is generated next,
    so staff aren't retyping it for every one of the 4 stage
    taps — type it once, tap through stages as needed, name carries
    over automatically. If the field is left blank, the message
    skips the greeting entirely rather than producing an awkward
    "Hi ," — build the greeting as `name ? "Hi " + name + ", " : ""`.
    4 stage buttons (Preparing Meal / Dispatched / Arrived /
    Delivered), each generating that stage's specific link AND a
    matching pre-written WhatsApp message with the name interpolated
    in (see the MESSAGES object in the script — one message template
    per stage, don't make staff compose messages by hand). The full
    MESSAGE (not just the bare link) is shown in a copyable text box
    with both a "Copy Message" and an "Open in WhatsApp" button — the
    whole point is staff can copy-paste-send without typing anything
    beyond the name field.

    NOT A DASHBOARD — IMPORTANT DISTINCTION IF ASKED TO EXPAND THIS:
